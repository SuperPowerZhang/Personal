## 1. JS 沙箱隔离

### 概念讲解

微前端中，多个子应用共享同一个浏览器环境，需要防止全局变量污染。主流方案：

| 方案 | 原理 | 优缺点 |
|------|------|---------|
| **Proxy 沙箱** | `new Proxy(window)` 拦截读写 | 性能好，支持多实例；不支持 IE |
| **快照沙箱** | 进入时快照 window，退出时恢复 | 兼容性好；只支持单实例，性能差 |
| **with + eval** | `with(fakeWindow) { eval(code) }` | 简单；安全性差 |

### 面试问题

**Q: JS 隔离的 Proxy 方案具体怎么实现的？局限是什么？**

### 参考答案

**Proxy 沙箱核心思路：**
1. 创建一个空对象 `fakeWindow` 作为子应用的 window 代理
2. 使用 `Proxy` 拦截所有属性的 get/set
3. set 操作写入 `fakeWindow`，不污染真实 window
4. get 操作先查 `fakeWindow`，没有则回退到真实 window

**局限：**
- 无法拦截 `document.createElement`、`addEventListener` 等原生 DOM API
- `eval` 内的代码默认绑定真实 window，需额外处理
- iframe 内的全局变量不经过 Proxy
- 某些第三方库直接操作 `window.xxx` 赋值（如 jQuery 插件），可能绕过沙箱

### 代码示例

```javascript
// 简化版 Proxy 沙箱实现
class ProxySandbox {
  constructor(name) {
    this.name = name;
    this.running = false;
    const fakeWindow = Object.create(null);

    this.proxy = new Proxy(fakeWindow, {
      get(target, prop) {
        // 优先从 fakeWindow 取值
        if (prop in target) {
          return target[prop];
        }
        // 回退到真实 window
        const value = window[prop];
        // 绑定 this 到 window（原生方法需要）
        if (typeof value === 'function' && !value.prototype) {
          return value.bind(window);
        }
        return value;
      },

      set(target, prop, value) {
        if (this.running) {
          target[prop] = value;
        }
        return true;
      },

      has(target, prop) {
        return prop in target || prop in window;
      },
    });
  }

  activate() {
    this.running = true;
  }

  deactivate() {
    this.running = false;
  }
}

// 使用示例
const sandbox = new ProxySandbox('app1');
sandbox.activate();

// 子应用代码在沙箱中执行
((window) => {
  window.myGlobal = 'hello'; // 写入 fakeWindow
  console.log(window.myGlobal); // 'hello'
  console.log(window.document); // 回退到真实 document
})(sandbox.proxy);

sandbox.deactivate();
console.log(window.myGlobal); // undefined — 未污染全局
```

```javascript
// 快照沙箱（兼容方案）
class SnapshotSandbox {
  constructor() {
    this.snapshot = {};
    this.modifiedProps = {};
  }

  activate() {
    // 进入前快照
    this.snapshot = {};
    for (const key in window) {
      this.snapshot[key] = window[key];
    }
    // 恢复上次的修改
    Object.keys(this.modifiedProps).forEach(key => {
      window[key] = this.modifiedProps[key];
    });
  }

  deactivate() {
    // 退出时记录修改并恢复
    this.modifiedProps = {};
    for (const key in window) {
      if (window[key] !== this.snapshot[key]) {
        this.modifiedProps[key] = window[key];
        window[key] = this.snapshot[key];
      }
    }
  }
}
```

## 2. CSS 隔离

### 概念讲解

| 方案 | 原理 | 适用场景 |
|------|------|----------|
| **CSS Modules** | 编译时生成唯一 className | 子应用内部样式 |
| **Shadow DOM** | 浏览器原生样式隔离 | 严格隔离需求 |
| **BEM/命名空间** | 人工约定前缀 | 简单场景 |
| **Dynamic Stylesheet** | 子应用切换时动态卸载/加载 CSS | qiankun 默认方案 |
| **postcss-prefix** | 编译时为所有选择器加前缀 | 批量处理 |

### 面试问题

**Q: 微前端中 CSS 隔离有哪些方案？各自适用什么场景？**

### 参考答案

**推荐组合方案：**
- 子应用内部：CSS Modules（开发体验好，零运行时开销）
- 子应用间：动态样式表（切换时卸载前一个子应用的 `<style>` 标签）
- 严格隔离：Shadow DOM（但会导致弹窗/Dropdown 定位问题）

**qiankun 的 CSS 隔离机制：**
- `strictStyleIsolation: true`：用 Shadow DOM 包裹子应用
- `experimentalStyleIsolation: true`：为子应用的所有 CSS 规则加前缀 `div[data-qiankun="appName"]`

### 代码示例

```javascript
// 方案1: 动态样式表隔离
class StyleSandbox {
  constructor(appName) {
    this.appName = appName;
    this.styles = [];
  }

  // 子应用激活时：收集其添加的 style 标签
  activate() {
    const observer = new MutationObserver((mutations) => {
      mutations.forEach(m => {
        m.addedNodes.forEach(node => {
          if (node.tagName === 'STYLE' || node.tagName === 'LINK') {
            this.styles.push(node);
          }
        });
      });
    });
    observer.observe(document.head, { childList: true });
    this.observer = observer;
  }

  // 子应用卸载时：移除其样式
  deactivate() {
    this.observer?.disconnect();
    this.styles.forEach(style => style.remove());
  }

  // 子应用重新激活：恢复样式
  reactivate() {
    this.styles.forEach(style => document.head.appendChild(style));
  }
}
```

```css
/* 方案2: postcss-prefix — 编译时自动加前缀 */

.btn { background: blue; }

/* 编译后 */

.app1 .btn { background: blue; }
```

## 3. 子应用通信

### 概念讲解

| 方案 | 适用场景 | 优缺点 |
|------|----------|---------|
| **Props 下发** | 主→子单向传递 | 简单直接；只能单向 |
| **CustomEvent** | 任意应用间 | 解耦；调试难 |
| **共享 Store** | 全局状态同步 | 统一管理；耦合度高 |
| **URL 参数** | 跨应用导航 | 天然持久化；容量有限 |

### 面试问题

**Q: 子应用之间如何共享状态？**

### 参考答案

**推荐分层方案：**
- **全局状态**（登录信息、权限）：主应用通过 props 下发 + 共享 store
- **临时通信**（事件通知）：CustomEvent 或 EventBus
- **路由联动**：统一由主应用管理路由

### 代码示例

```typescript
// 方案1: 基于发布订阅的全局通信
class MicroEventBus {
  private events = new Map<string, Set<Function>>();

  on(event: string, callback: Function) {
    if (!this.events.has(event)) {
      this.events.set(event, new Set());
    }
    this.events.get(event)!.add(callback);
    return () => this.events.get(event)?.delete(callback); // 返回取消函数
  }

  emit(event: string, data?: any) {
    this.events.get(event)?.forEach(cb => cb(data));
  }
}

// 挂载到全局，所有子应用共享
window.__MICRO_EVENT_BUS__ = new MicroEventBus();

// 子应用 A：发布事件
window.__MICRO_EVENT_BUS__.emit('user:updated', { id: 1, name: 'test' });

// 子应用 B：订阅事件
const unsubscribe = window.__MICRO_EVENT_BUS__.on('user:updated', (user) => {
  console.log('User updated:', user);
});
// 卸载时取消
unsubscribe();
```

## 4. 路由管理

### 概念讲解

微前端路由的核心挑战：主应用和子应用各自有路由系统，如何协调？

**典型方案：**
- 主应用监听 URL 变化 → 匹配激活规则 → 加载/卸载子应用
- 子应用使用自己的 Router，但 base path 由主应用指定

### 面试问题

**Q: 微前端路由分发机制是怎样的？**

### 参考答案

## 5. 共享依赖策略

### 面试问题

**Q: 微前端下公共依赖怎么处理（避免重复加载）？**

### 参考答案

| 策略 | 实现 | 风险 |
|------|------|------|
| **Externals + CDN** | 主应用加载 React/ReactDOM CDN，子应用 external | 版本强一致 |
| **Webpack Module Federation** | 运行时共享模块 | 配置复杂 |
| **Import Map** | 浏览器原生模块映射 | 兼容性 |
| **主应用注入** | 主应用 window 挂载，子应用直接用 | 耦合高 |

### 代码示例

```javascript
// Webpack 5 Module Federation — 最灵活的共享方案
// 主应用 webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      shared: {
        react: { singleton: true, requiredVersion: '^18.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
        antd: { singleton: true, requiredVersion: '^5.0.0' },
        dayjs: { singleton: true },
      },
    }),
  ],
};

// 子应用 webpack.config.js
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'finance',
      filename: 'remoteEntry.js',
      exposes: {
        './App': './src/App.tsx',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
        antd: { singleton: true, requiredVersion: '^5.0.0' },
        dayjs: { singleton: true },
      },
    }),
  ],
};
```

## 6. 方案对比

### 面试问题

**Q: 微前端 vs Monorepo vs iframe，各自适用场景？**

### 参考答案

| 维度 | 微前端 | Monorepo | iframe |
|------|--------|----------|--------|
| 隔离性 | 中（需沙箱） | 无（共享运行时） | 强（天然隔离） |
| 通信 | 需设计 | 直接引用 | postMessage |
| 独立部署 | ✅ | ❌（需统一构建） | ✅ |
| 独立技术栈 | ✅ | ❌ | ✅ |
| 性能 | 好 | 最好 | 差（每个 iframe 独立上下文） |
| 体验 | 无感 | 无感 | 弹窗/路由/滚动割裂 |
| 适用场景 | 大团队、异构技术栈、独立发版 | 同技术栈、共享组件、统一构建 | 第三方嵌入、强隔离需求 |

**选择建议：**
- 同团队同技术栈 → Monorepo
- 多团队异构、需独立部署 → 微前端
- 嵌入不可控的第三方页面 → iframe
