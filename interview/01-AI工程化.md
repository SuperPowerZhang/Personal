## 1. MCP (Model Context Protocol)

### 概念讲解

MCP 是 Anthropic 提出的开放标准协议，定义了 AI 应用与外部数据源/工具之间的通信方式。类比 USB-C 接口——不管什么设备，只要遵循这个协议就能互联。

**架构组成：**
- **MCP Host**：发起连接的 AI 应用（如 Claude Code、IDE 插件）
- **MCP Client**：在 Host 内部，维护与 Server 的 1:1 连接
- **MCP Server**：提供具体能力的轻量服务（如 Jira Server、GitHub Server）
- **传输层**：stdio（本地）或 SSE/HTTP（远程）

**三大能力原语：**
- **Tools**：模型可调用的函数（如 `jira_search_issues`）
- **Resources**：模型可读取的数据（如文件内容、DB 记录）
- **Prompts**：预定义的提示模板

### 面试问题

**Q: MCP Server 架构是什么？你解决的 v2/v3 兼容问题具体是什么？**

### 参考答案

MCP Server 本质是一个暴露 Tools/Resources/Prompts 的服务进程。以 Jira MCP Server 为例：

1. Claude（Host）通过 stdio 启动 Jira MCP Server 进程
2. Server 启动时读取配置（Jira URL、token）
3. 注册 tools：`jira_get_issue`、`jira_search_issues`、`jira_add_comment` 等
4. Claude 调用 tool → Server 转发为 Jira REST API 请求 → 返回结果

**v2/v3 兼容问题：**

开源 Jira MCP Server 默认使用 Jira Cloud API v3（REST `/rest/api/3/...`），但公司部署的是 Jira Data Center（自托管版本），只支持 API v2（`/rest/api/2/...`）。

差异点：
- v3 使用 ADF（Atlassian Document Format）富文本结构
- v2 使用纯文本/wiki markup
- 部分端点路径和响应结构不同

**解决方案：** 启动时自动检测 Jira 实例版本（通过 `/rest/api/2/serverInfo`），如果是 Data Center 则自动将请求路径降级到 v2，并将 ADF 内容转换为 wiki markup 格式。

### 代码示例

```typescript
// MCP Server 启动时的版本检测与自动修复
async function detectJiraVersion(baseUrl: string, token: string) {
  try {
    const res = await fetch(`${baseUrl}/rest/api/2/serverInfo`, {
      headers: { Authorization: `Bearer ${token}` }
    });
    const info = await res.json();
    // Data Center 返回 deploymentType: "Server"
    // Cloud 返回 deploymentType: "Cloud"
    return info.deploymentType === 'Cloud' ? 'v3' : 'v2';
  } catch {
    return 'v2'; // 降级兜底
  }
}

// 根据版本选择 API 路径
function getApiPath(version: 'v2' | 'v3', endpoint: string) {
  return `/rest/api/${version === 'v3' ? '3' : '2'}/${endpoint}`;
}

// ADF → wiki markup 转换（v2 不支持 ADF）
function adfToWikiMarkup(adf: any): string {
  if (!adf || !adf.content) return '';
  return adf.content.map((node: any) => {
    switch (node.type) {
      case 'paragraph':
        return node.content?.map((c: any) => c.text || '').join('') + '\n';
      case 'heading':
        const level = 'h' + (node.attrs?.level || 1);
        return `${level}. ${node.content?.map((c: any) => c.text).join('')}\n`;
      default:
        return '';
    }
  }).join('');
}
```

## 2. AI Agent

### 概念讲解

Agent 是具有自主决策和行动能力的 AI 系统。与普通 LLM 调用的核心区别：

| 维度 | 普通 LLM 调用 | AI Agent |
|------|-------------|----------|
| 交互模式 | 单次输入→输出 | 多轮循环（ReAct loop） |
| 工具使用 | 无或固定 pipeline | 动态选择工具 |
| 规划能力 | 无 | 有（分解子任务） |
| 记忆 | 无状态 | 有上下文/长期记忆 |
| 自主性 | 被动响应 | 主动决策下一步 |

**Agent 核心循环（ReAct Pattern）：**
```
Thought → Action → Observation → Thought → ... → Final Answer
```

### 面试问题

**Q: Agent 和普通 LLM 调用的区别是什么？如何设计一个可靠的 Agent 系统？**

### 参考答案

**区别已如上表。设计可靠 Agent 系统的关键：**

1. **明确的 Tool 定义**：每个 tool 有清晰的 name、description、input schema，让 LLM 能正确选择
2. **错误处理与重试**：tool 执行失败时，将错误信息反馈给 LLM，让它决定重试或换策略
3. **Guard Rails**：限制最大循环次数、敏感操作需确认、token budget 控制
4. **结构化输出**：关键步骤要求 LLM 按 JSON Schema 输出，避免解析失败
5. **可观测性**：记录每一步的 thought/action/observation，便于调试

### 代码示例

```typescript
// 简化版 Agent 循环
interface Tool {
  name: string;
  description: string;
  parameters: Record<string, any>;
  execute: (params: any) => Promise<string>;
}

async function agentLoop(
  query: string,
  tools: Tool[],
  maxIterations = 10
) {
  const messages: Message[] = [
    { role: 'system', content: buildSystemPrompt(tools) },
    { role: 'user', content: query }
  ];

  for (let i = 0; i < maxIterations; i++) {
    const response = await llm.chat(messages, {
      tools: tools.map(t => ({
        type: 'function',
        function: { name: t.name, description: t.description, parameters: t.parameters }
      }))
    });

    // LLM 决定不再调用工具 → 返回最终答案
    if (!response.tool_calls?.length) {
      return response.content;
    }

    // 执行工具调用
    for (const call of response.tool_calls) {
      const tool = tools.find(t => t.name === call.function.name);
      try {
        const result = await tool.execute(JSON.parse(call.function.arguments));
        messages.push({
          role: 'tool',
          tool_call_id: call.id,
          content: result
        });
      } catch (err) {
        messages.push({
          role: 'tool',
          tool_call_id: call.id,
          content: `Error: ${err.message}`
        });
      }
    }
  }

  throw new Error('Agent exceeded max iterations');
}
```

## 3. RAG (Retrieval-Augmented Generation)

### 概念讲解

RAG 解决 LLM 知识截止、幻觉问题。流程：

```
用户问题 → Embedding → 向量检索 → 取 Top-K 文档 → 注入 prompt → LLM 生成答案
```

**关键组件：**
- **Embedding 模型**：将文本转为向量（如 OpenAI text-embedding-3-small）
- **向量数据库**：存储和检索向量（Pinecone、Milvus、pgvector）
- **Chunking 策略**：文档切片方式影响检索质量
- **Reranking**：粗检索后用交叉编码器精排

### 面试问题

**Q: RAG 系统中如何优化检索质量？**

### 参考答案

1. **Chunking 优化**：按语义段落切分而非固定长度；保留 overlap（如 chunk_size=512, overlap=64）
2. **Hybrid Search**：向量检索 + 关键词检索（BM25）混合，互补短板
3. **Query Transformation**：将用户问题改写为多个子查询，扩大召回
4. **Metadata Filtering**：利用文档元数据（时间、来源、标签）预过滤
5. **Reranking**：用 Cross-Encoder 对 Top-K 结果重排序
6. **Contextual Retrieval**：为每个 chunk 添加上下文描述（Anthropic 方案）

### 代码示例

```typescript
// 基于 LangChain 的 RAG pipeline 简化示例
import { OpenAIEmbeddings } from '@langchain/openai';
import { PGVectorStore } from '@langchain/community/vectorstores/pgvector';

// 1. 文档切片
function chunkDocument(text: string, chunkSize = 512, overlap = 64): string[] {
  const chunks: string[] = [];
  let start = 0;
  while (start < text.length) {
    chunks.push(text.slice(start, start + chunkSize));
    start += chunkSize - overlap;
  }
  return chunks;
}

// 2. 检索 + 生成
async function ragQuery(question: string, vectorStore: PGVectorStore) {
  // 向量检索 Top-K
  const docs = await vectorStore.similaritySearch(question, 5);

  // 构造 prompt
  const context = docs.map(d => d.pageContent).join('\n---\n');
  const prompt = `基于以下参考资料回答问题。如果资料中没有答案，说明不确定。

参考资料：
${context}

问题：${question}`;

  const answer = await llm.generate(prompt);
  return { answer, sources: docs };
}
```

## 4. AI Code Review Pipeline

### 概念讲解

AI Code Review 系统的典型流程：

```
MR/PR 触发 → 获取 diff → 分片处理 → LLM 审查 → 结构化输出 → 发布评论
```

### 面试问题

**Q: AI Code Review 的 pipeline 是怎样的？如何保证 review 质量？**

### 参考答案

**Pipeline 设计：**

1. **Webhook 触发**：GitLab/GitHub MR 事件 → 触发 review 任务
2. **Diff 解析**：获取变更文件列表、逐文件 diff、上下文代码
3. **分片策略**：大 diff 按文件拆分，每个文件独立 review；超长文件按 hunk 拆分
4. **Prompt 工程**：
   - System prompt 定义审查维度（bug/性能/安全/可读性）
   - 注入项目规范（ESLint 规则、命名约定）
   - few-shot 示例提升输出质量
5. **结构化输出**：要求 LLM 按 JSON Schema 输出（文件名、行号、问题类型、建议）
6. **去重过滤**：历史相同 comment 不重复发布
7. **评论发布**：通过 GitLab/GitHub API 在对应行发 inline comment

**质量保证手段：**
- 多维度审查（bug、perf、security、style 分开 prompt）
- 置信度字段，低置信度的发现标记为 suggestion 而非 error
- 人工反馈循环：reviewer 标记"有用/无用"，优化 prompt
- 误报率监控：追踪被 dismiss 的评论比例

### 代码示例

```typescript
// AI Code Review 核心结构
interface ReviewFinding {
  file: string;
  line: number;
  severity: 'error' | 'warning' | 'suggestion';
  category: 'bug' | 'performance' | 'security' | 'style';
  description: string;
  suggestion?: string;
  confidence: number; // 0-1
}

async function reviewFile(diff: FileDiff, context: string): Promise<ReviewFinding[]> {
  const prompt = `你是高级代码审查员。审查以下代码变更，找出潜在问题。

## 变更文件：${diff.filename}

## Diff:
\`\`\`
${diff.patch}
\`\`\`

## 完整文件上下文（前后 50 行）:
\`\`\`
${context}
\`\`\`

## 输出格式
返回 JSON 数组，每个元素包含：file, line, severity, category, description, suggestion, confidence`;

  const response = await llm.generate(prompt, {
    response_format: { type: 'json_object' }
  });

  const findings: ReviewFinding[] = JSON.parse(response);
  // 过滤低置信度
  return findings.filter(f => f.confidence > 0.7);
}
```

## 5. Prompt Engineering

### 概念讲解

**核心技巧：**
- **System Prompt**：定义角色、约束、输出格式
- **Few-shot**：提供输入-输出示例，引导模式
- **Chain of Thought (CoT)**：要求模型"逐步思考"
- **Self-consistency**：多次采样取多数答案
- **Structured Output**：JSON Schema / 模板约束

### 面试问题

**Q: 如何设计一个好的 System Prompt？有哪些常见反模式？**

### 参考答案

**好的 System Prompt 结构：**
1. 角色定义（你是...）
2. 任务描述（你需要...）
3. 约束条件（不要.../必须...）
4. 输出格式（按以下 JSON 格式...）
5. 示例（输入→输出）

**常见反模式：**
- 指令矛盾（"简洁回答"又要求"详细解释"）
- 过度约束导致模型难以遵循
- 没有输出格式定义，导致解析困难
- 重要指令放在 prompt 末尾而非开头

### 代码示例

```typescript
// 结构化 Prompt 模板
const systemPrompt = `你是一个代码审查专家。

## 任务
审查用户提交的代码变更，识别潜在问题。

## 审查维度
1. 正确性：逻辑错误、边界条件
2. 性能：不必要的重渲染、O(n²) 操作
3. 安全：XSS、注入、敏感信息泄露

## 约束
- 只关注变更的代码，不评论未修改部分
- 每个问题必须指出具体行号
- 不确定的问题标记 confidence < 0.5

## 输出格式
\`\`\`json
{
  "findings": [
    {
      "line": 42,
      "severity": "warning",
      "category": "performance",
      "description": "...",
      "suggestion": "..."
    }
  ],
  "summary": "一句话总结"
}
\`\`\``;
```

## 6. 如何评估 AI 辅助工具的 ROI

### 面试问题

**Q: 如何评估 AI 辅助工具的效果？**

### 参考答案

**量化指标：**

| 指标 | 计算方式 |
|------|----------|
| Review 覆盖率 | AI review 的 MR 数 / 总 MR 数 |
| 有效发现率 | 被采纳的 comment / 总 comment |
| 误报率 | 被 dismiss 的 comment / 总 comment |
| 时间节省 | 人工 review 平均时间 - (AI review 后人工修订时间) |
| Bug 拦截率 | AI 发现的真实 bug / 后续 production bug 总数 |

**定性指标：**
- 开发者满意度调查（NPS）
- Review 等待时间缩短
- 代码质量趋势（SonarQube 指标变化）

**推广策略：**
- 先在小范围试点，收集数据
- 用 A/B 组对比有/无 AI review 的 bug 率
- 定期 retro 收集反馈，迭代 prompt
