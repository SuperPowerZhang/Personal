## 1. 需求管理与排期

### 面试问题

**Q: Finance 域多少人？你怎么分配需求和排期？**

### 参考答案

**团队规模与分工（参考答案模板，根据实际调整）：**

Finance 域前端 X 人（含我），后期支持 Claim、UW 扩展到三域并行。

**排期方法：**

1. **需求评审**：PM 提需求 → 前端评估复杂度（T-shirt sizing: S/M/L/XL）
2. **拆分与估时**：大需求拆子任务，每个子任务 ≤ 3 天
3. **分配原则**：
   - 模块 owner 制：每个子模块有固定负责人，熟悉度最高
   - 新人搭配 mentor：简单需求给新人做，复杂需求 owner 负责
   - Buffer 预留：每个 sprint 预留 20% 给技术债和线上问题
4. **跟踪**：每日 standup 同步进度，Jira 看板更新状态
5. **风险控制**：超过预估 50% 时立即升级，提前暴露而非最后一天说做不完

**三域并行策略：**
- 每域指定 1 个 backup，避免单点
- 需求优先级排序：P0（线上 bug）> P1（本迭代核心）> P2（可延后）
- 并行不代表每个域都要我 review，培养每域 owner 独立决策能力

## 2. 技术债治理

### 面试问题

**Q: 技术债治理如何平衡业务需求？你怎么说服 PM 给排期？**

### 参考答案

**平衡策略：**

1. **量化影响**：不说"代码质量差"，说"构建慢 75s 导致 CI 每天浪费 X 分钟"、"Moment 占 bundle 300KB 影响首屏加载"
2. **搭车原则**：业务需求涉及的模块顺便治理（不额外排期）
3. **专项窗口**：每个 sprint 预留 1-2 天做纯技术改进
4. **ROI 排序**：治理优先级 = 影响范围 × 风险程度 × 治理成本倒数

**说服 PM 的话术（真实案例）：**

> "Moment.js → Day.js 迁移，预计 3 天工作量。效果：bundle 减小 1.12MB（-10%），首屏加载提升 XX ms。每个用户每次访问都受益，且后续所有新代码直接用轻量库。"

> "umi → rspack 迁移，预计 5 天。效果：每次构建快 45s，CI 一天跑 30 次 = 每天节省 22 分钟等待时间。开发体验改善，HMR 从 5s→1s。"

**关键原则：**
- 永远用数据说话
- 和业务关联（不是"代码更优雅"，是"用户体验更好"/"交付更快"）
- 增量推进，不要一次性大重构
- 做完记录文档，形成可复制的迁移指南给其他域

## 3. 跨团队推动

### 面试问题

**Q: 跨团队推动（如组件库复用）遇到阻力怎么处理？**

### 参考答案

**常见阻力与应对：**

| 阻力 | 应对 |
|------|------|
| "我们有自己的组件" | 对比两者实现，找到差异点；不是替换而是统一，保留各自合理部分 |
| "没时间迁移" | 提供迁移脚本/codemod；新需求直接用新组件，旧的渐进替换 |
| "你们的组件不满足我的需求" | 收集需求差异，共同设计 API；组件库应服务所有域 |
| "改了万一出 bug 怎么办" | 提供测试用例、migration guide；小范围试点再推广 |

**我的实际做法：**
1. **先做示范**：Finance 域先完成全量迁移，跑出数据（bundle 减少多少、bug 减少多少）
2. **输出文档**：迁移指南、FAQ、踩坑记录，其他域可自助参考
3. **组织分享**：跨组技术分享会展示收益和方法
4. **找到盟友**：先说服一个愿意配合的域，两个域成功后第三个更容易
5. **向上借力**：如果纯靠说服推不动，找技术负责人在全域层面定方向

## 4. 新人 Onboarding

### 面试问题

**Q: 新人 onboarding 你怎么做的？**

### 参考答案

**结构化 Onboarding 计划：**

| 时间 | 内容 | 目标 |
|------|------|------|
| Day 1-2 | 环境搭建 + 项目架构介绍 + 开发规范文档 | 能跑通项目 |
| Day 3-5 | 认领简单 bug/小需求 | 走通完整开发流程（开发→review→上线） |
| Week 2 | 参与一个 M 级需求 | 熟悉业务背景 |
| Week 3-4 | 独立负责一个完整需求 | 可以独立交付 |
| Month 2 | 开始做 Code Review | 融入团队规范 |

**关键实践：**
- **文档先行**：README、架构图、常见问题 FAQ 提前准备好
- **Buddy 制**：指定 1 个人随时回答问题（不一定是 leader）
- **逐步放权**：不要一上来就给大需求，也不要一直给简单任务
- **代码规范强制**：ESLint + Prettier + pre-commit hook 自动化，减少 review 中的规范性讨论
- **定期 1on1**：了解卡点和感受，及时调整

## 5. 技术分享

### 面试问题

**Q: 技术分享怎么组织？频率和效果如何评估？**

### 参考答案

**组织方式：**
- **频率**：每两周一次，每次 30-45 分钟
- **轮值制**：每人轮流主讲，确保所有人都有输出
- **主题来源**：
  - 项目中踩过的坑
  - 新技术调研
  - 优秀实践分享
  - Code Review 中发现的通用问题

**效果评估：**
- **直接指标**：分享后是否有人在项目中应用了分享的技术/方案
- **间接指标**：团队 Code Review 中同类问题减少
- **反馈收集**：简单打分（1-5），对下次选题的建议

**Shopee 全英文分享经历补充：**
- 跨国团队（新加坡、中国、印度），全英文
- 降低语言门槛：提前准备 slides 和 demo，减少即兴表达压力
- 鼓励互动：每次分享预留 10 分钟 Q&A

## 6. 流程沉淀

### 面试问题

**Q: 你提到"梳理开发流程与技术文档"，具体做了什么？**

### 参考答案

**文档体系：**

1. **开发规范**：
   - Git 分支策略（feature → dev → staging → master）
   - Commit message 规范（Conventional Commits）
   - Code Review checklist
   - 命名规范、目录结构规范

2. **技术文档**：
   - 微前端架构图 + 子应用接入指南
   - 公共组件使用文档（props/API/示例）
   - 部署流程（CI/CD pipeline 说明）
   - 环境配置（本地/测试/预发/生产）

3. **迁移指南**：
   - Moment → Day.js 迁移手册
   - Antd 3 → Antd 5 升级指南
   - umi → rspack 迁移步骤

**核心理念：** 文档不是写了就完了——要放在团队随时能找到的地方（Confluence/飞书），新人 onboarding 时验证是否还准确，版本更新时同步维护。

## 7. 冲突管理

### 面试问题

**Q: 团队中遇到技术方案分歧怎么处理？**

### 参考答案

**处理步骤：**

1. **明确评估标准**：先统一用什么维度来比较（性能？可维护性？迁移成本？）
2. **数据说话**：不是"我觉得 A 好"，而是"方案 A 在 XX 场景下比 B 快 30%"
3. **原型验证**：真有争议就花半天各做个 POC，用事实说话
4. **有时效性**：不要无限讨论，设定决策时限（如 1 天内决定）
5. **Disagree and commit**：一旦决定，即使有人不完全认同，也全力执行

**避免的反模式：**
- 级别压人（"我是 leader 所以听我的"）
- 无止境辩论
- 翻旧账（"上次你的方案就出了问题"）
